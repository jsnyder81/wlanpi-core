# Unified Authentication for wlanpi-core (MCP-ready)

## Context

A new MCP server (`wlanpi-mcp`) will consume wlanpi-core. Today core runs two schemes: HMAC-SHA256 with a machine-wide root-owned secret for loopback clients, and DB-backed HS256 "JWTs" for everyone else, with nginx choosing the path by spoofing `X-Real-IP` off an `X-Wlanpi-Client: mcp` header. Friction is already visible: the MCP service can't read the HMAC secret (hence the header hack), JWT expiry is not enforced (`time_validation_enabled = False` in `wlanpi_core/core/token.py:121`), tokens are symmetric so only core can verify them, and every new service needs bespoke integration.

**Goals:** improved security, simpler integration for additional services, one credential story for users.

**Constraints:** LAN + occasional remote threat model; tokens should be OAuth-shaped (scopes/expiry/JWKS) but a full OAuth 2.1 server is not required yet; bootstrap via an on-device pairing flow; **the HMAC path must remain** for legacy on-box clients (touch UI, getjwt, lhapitest, FPMS).

## Recommended approach: Option B — OAuth-shaped device token service

Core becomes a small, standards-shaped token issuer. Everything except legacy HMAC clients uses one mechanism: short-lived, asymmetrically signed bearer tokens.

### Design

1. **Asymmetric signing (EdDSA/Ed25519, ES256 fallback)** — replace HS256 signing keys in `TokenManager` (`wlanpi_core/core/token.py`) with an Ed25519 keypair generated by `SecurityManager` (`wlanpi_core/core/security.py`) alongside the existing secrets in `SECRETS_DIR`. `authlib` (already a dependency) supports both.
2. **Publish JWKS** — new unauthenticated endpoints `GET /.well-known/jwks.json` and minimal `GET /.well-known/oauth-authorization-server` metadata. Any service (the MCP server, webui, future daemons) can verify tokens locally without calling core or sharing secrets.
3. **Enforce token semantics (clock-aware)** — enforce `exp`/`iat` with ~10 min leeway, add `aud` (=`wlanpi-core`) and `scope` claims (e.g. `system:read network:write capture` mapped per-router). Access-token TTL: 8–24 h (see the No-RTC section — short TTLs are not viable, and DB-backed revocation makes them unnecessary).
4. **Per-client credentials + refresh** — replace "anyone with the HMAC secret mints a 7-day token" with a client registry (extend the existing `devices` table in `wlanpi_core/core/models.py`): each client gets a `client_id` + long-lived revocable refresh token (hashed at rest). `POST /auth/token` grows `grant_type=refresh_token`. **DB-backed validation (token row exists, not revoked) remains the primary, permanent control on core** — it is clock-independent; `exp` is defense-in-depth. Revoking a client kills its refresh token *and* its live access tokens immediately via the DB check.
5. **On-device pairing flow** — a CLI (`wlanpi-core pair`, evolving `wlanpi_core/cli/getjwt.py`) and/or a device web page that mints a client credential with chosen scopes; display as QR/copy-paste for remote clients like the MCP consumer. Pairing runs on-box (HMAC- or root-gated), so physical/admin access remains the root of trust.
6. **First-class on-box service credentials** — provision the MCP server (and future unprivileged services) a client credential at install time via systemd `LoadCredential=` or a per-service secret file, removing the `X-Wlanpi-Client` nginx map hack in `install/etc/wlanpi-core/nginx/wlanpi_core.conf`.
7. **HMAC path untouched** — `verify_hmac` (`wlanpi_core/core/auth.py:57`) and the loopback branch of `verify_auth_wrapper` stay as-is for legacy clients.
8. **Cross-cutting hardening** (do regardless) — add auth to the currently unauthenticated capture WebSocket (`/api/v1/streaming/capture`); offer TLS on port 31415 (self-signed device cert, trust-on-first-use) for the remote use case.

## No-RTC clock considerations (WLAN Pi platforms have no RTC)

None of the target platforms (RPi4/CM4 etc.) have a hardware RTC; the clock is restored by fake-hwclock at boot and only becomes accurate after NTP sync — which may never happen on isolated test networks. This is almost certainly why `time_validation_enabled = False` exists today. Consequences for this design:

- **Never make wall-clock the sole security control.** The DB-backed existence/revoked check on core is the authoritative validity mechanism (works with any clock). Time claims are best-effort hardening.
- **Sync-gated enforcement:** core enforces `exp`/`iat` only when the clock is known-synced — check systemd-timesyncd's `/run/systemd/timesync/synchronized` (or `timedatectl show -p NTPSynchronized`). Unsynced → DB-only validation + a logged warning. Cache the sync check (it flips rarely).
- **Leeway:** ±10 min skew tolerance on all time-claim checks; document the same for off-box verifiers (MCP server verifying via JWKS).
- **TTL:** 8–24 h access tokens instead of minutes. Immediate revocation comes from the DB check, not TTL, so long TTLs cost little and survive skew/offline operation.
- **Issuance while unsynced:** still issue (can't strand offline users); stamp claims from best-known time, log a warning, and have the pairing CLI print "clock not synced — remote verifiers may reject timestamps on this token."
- **Off-box verifiers:** JWKS gives them offline signature/claim verification, but authoritative revocation stays with core; a verifier needing hard guarantees can hit an introspection-style check (or just let core's own per-request validation be the gate, since every API call lands on core anyway).

## Why B over the alternatives

- **A (just harden existing JWT):** smallest diff but keeps symmetric keys, so every verifier must call core; doesn't simplify multi-service integration.
- **C (full OAuth 2.1 server):** MCP-native but heavy; interactive OAuth flows on a headless bench device want TLS + stable hostnames; premature for the current consumer count. B's claims/endpoints are forward-compatible so C can be layered on later without breaking clients.
- **D (mTLS):** strong but terrible provisioning UX for MCP clients/browsers; no scopes; would still need a token story anyway.
- **E (static API keys):** fails the security and lifecycle goals.

## Phasing

- **Phase 1 (core hardening):** Ed25519 signing, JWKS + metadata endpoints, enforce `exp`/`iat`, add `scope`/`aud`, auth on capture WS.
- **Phase 2 (credential lifecycle):** client registry, refresh grant, revocation endpoint, pairing CLI/web flow, systemd-provisioned MCP credential, remove nginx header map.
- **Phase 3 (optional, later):** full OAuth 2.1 (authorization-code + PKCE, dynamic client registration) for MCP-native client auth; TLS by default.

## Verification

- Unit tests for claim enforcement (expired token rejected when clock synced, accepted with DB-only validation when unsynced, wrong `aud`/`scope` rejected, revoked refresh token rejected).
- Clock-skew test: issue a token, shift the mocked clock hours backward/forward, confirm DB-backed validation keeps working and revocation still bites.
- End-to-end on a dev box: pair a client, obtain an access token, call scoped endpoints, verify the token against JWKS from a separate process (simulating the MCP server), revoke, confirm refresh fails and the access token dies at TTL.
- Regression: legacy HMAC clients (`lhapitest`, `getjwt`) still work over loopback.
